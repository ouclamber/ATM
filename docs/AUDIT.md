## 2. Дыры в архитектуре

| # | Проблема | Почему важно | Что сделано |
|---|----------|--------------|-------------|
| A1 | **Нет защиты от параллельных изменений.** Два сеанса/банкомата читают баланс 1000 ₽, оба списывают по 1000 ₽, второе сохранение затирает первое. То же с кассетами. | Классический lost update — деньги «создаются из воздуха». | Оптимистическая блокировка по системной колонке PostgreSQL `xmin` для счетов и кассет (миграция `AddConcurrencyTokens` не меняет схему — `xmin` есть у каждой строки). `UnitOfWork` переводит `DbUpdateConcurrencyException` в `ConcurrencyConflictException` (Application не зависит от EF), обработчики возвращают `Error.Conflict` «повторите попытку». Проверено интеграционными тестами на реальной БД. |
| A2 | Презентационный слой держал EF-сущность `BankAccount` из уже закрытого `DbContext` и вызывал на ней доменные методы. | Обход сценариев, дублирование логики, расхождение данных. | `LoginHandler` возвращает DTO `AccountSummary`; `UserSession` хранит только его. |
| A3 | Меню были зарегистрированы как Scoped и резолвились из корневого провайдера (captive dependency, скрытая ошибка времени жизни). | При включённой валидации DI это исключение; без неё — неявный «вечный» scope. | Меню — Singleton с `IServiceScopeFactory`, scope создаётся на каждую операцию. Включены `ValidateScopes` и `ValidateOnBuild`. |
| A4 | Явная транзакция `BeginTransaction/Commit` в переводе вокруг одного `SaveChanges`. | Лишний код: `SaveChanges` и так атомарен; к тому же несовместимо с retry-стратегией EF. | Убрано, `IUnitOfWork` упрощён до `SaveChangesAsync`. Включён `EnableRetryOnFailure` для транзиентных сбоев сети. |
| A5 | Нет защиты админ-входа от перебора. | Пароль администратора перебирается без ограничений. | Блокировка на 5 минут после 5 неверных попыток (с `TimeProvider` для тестов). BCrypt проверяется всегда, даже при неверном логине, — время ответа не выдаёт, угадан ли логин. |
| A6 | Клиенту в «Информации о банкомате» показывалась сумма наличных в банкомате. | Лишняя информация для злоумышленника. | Клиент видит только доступные номиналы; сумма — в админ-панели. |
| A7 | Лимиты читались из конфигурации при каждом обращении без проверки. | Опечатка в конфиге всплывала посреди операции клиента. | `BankConfig` читает и валидирует лимиты один раз при старте. |
| A8 | Нет интеграционных тестов: миграции, маппинг value objects и запросы репозиториев не проверялись ни разу. | Ошибки маппинга находятся только у пользователя. | `Bankomat.Tests/Integration` — тесты на реальном PostgreSQL (seed, снятие, перевод, конфликты `xmin`). В CI PostgreSQL поднимается как service-контейнер. |

## 3. Оптимизации

| Что | Было | Стало |
|-----|------|-------|
| Подбор купюр | Жадный O(n), с ложными отказами | DP O(U·Σlog₂count), где U = сумма/100: для лимита 20 000 ₽ — ~200×50 операций, микросекунды; всегда находит решение, если оно есть, с минимумом купюр |
| Seed при каждом запуске | N запросов `GetByCardNumber` | Один запрос `WHERE card_number IN (...)`, BCrypt (специально медленный) не вызывается для существующих карт |
| Экраны только для чтения (история, кассеты, информация о банкомате, расчёт выдачи) | Отслеживаемые сущности | `AsNoTracking` |
| Валидация суммы в обработчиках | Часть проверок после запросов к БД | Все дешёвые проверки (сумма > 0, лимит, кратность, формат карты) — до обращения к БД |
| Загрузка банкомата | Лишний `Include` owned-коллекции | Убран (owned-типы загружаются автоматически) |
| История операций | Служебные записи «Вход» занимали место в лимите 50 строк | Фильтр по типу на стороне БД, лимит параметризован |
| Логи в консоль | Каждая операция писала в консоль | Только ошибки; полный лог — в файл |
| Дублирование | `MaskCard` ×3, `FormatBanknotes` ×3, однотипные блоки логирования | `LogFormat`, единый `Reject(...)` в обработчиках |

## 4. Спорные моменты — что решено

- **Сумма внесения вводилась вручную вместе с купюрами.** Теперь сумму считает банкомат по купюрам, клиент только подтверждает. Обработчик по-прежнему сверяет заявленную сумму с купюрами (точное сравнение `decimal` вместо допуска 0,01).
- **Снятие:** результат больше не исчезает через 2,5 секунды — экран ждёт нажатия клавиши. UI проверяет кратность 100 до запроса.
- **`launchSettings.json` и `BankomatBackend.http`** — остатки шаблона веб-API (URL, `ASPNETCORE_ENVIRONMENT`, weatherforecast). `launchSettings.json` заменён профилем консольного приложения, `.http` удалён.
- **Неиспользуемый пакет** `Microsoft.EntityFrameworkCore.InMemory` в тестах удалён.
- **`coverlet.runsettings`:** `Threshold` не действует в режиме `coverlet.collector` (только в msbuild-интеграции), поэтому README обещал порог 80%, который нигде не проверялся. Нерабочие настройки удалены, фактическое покрытие — 88,5%.
- **`--hash` без аргумента** раньше молча печатал хеш от `admin123`; теперь выводит подсказку и код возврата 2.
- **`BankConfig.cs`** лежал в папке `Persistence/Configurations`, но в namespace `Infrastructure.Configuration` — перенесён.

## 5. Что сознательно оставлено (рекомендации)

- **Вход по несуществующей карте** отвечает «Карта не найдена», а не общим «неверная карта или PIN». Для банкомата с физической картой это нормально, но для веб-интерфейса стоит унифицировать ответ.
- **Журнал входов и финансовые операции в одной таблице** `transactions`. Лучше разделить аудит и финансы; пока история просто фильтрует записи «Вход».
- **Нет журнала действий администратора** (кто пополнял кассеты) и разблокировки карт — это новые функции, а не исправления; оставлены в «Планах».
- **Пароль БД в `appsettings.json`** оставлен (`root`) для запуска «из коробки» с `docker-compose.yml`; для реального использования — переменная окружения или `appsettings.local.json`.
- **`Microsoft.NET.Test.Sdk 17.11.1`** выдаёт предупреждение `VSTEST_ARTIFACTS_DIRECTORY`; можно обновить до 17.14+ при следующем обновлении зависимостей.
- **`System.Security.Cryptography.Xml`** напрямую в коде не используется — вероятно, был добавлен, чтобы закрыть уязвимость транзитивной зависимости; оставлен без изменений.
